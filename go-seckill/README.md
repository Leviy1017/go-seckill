## 第一章：启程 — 认识 Web 后端与项目全景

### 1.1 核心概念：后端与 API 到底是什么？

**生活化比喻 — 你在淘宝下单的全过程**

你在淘宝 App 上看到一个秒杀商品，点击"立即抢购"。按下按钮的瞬间发生了什么？

你的手机（前端）把"用户 ID 是 12345，想买商品 ID 是 67890"打包成一个 HTTP 请求，发给了淘宝的服务器。服务器收到后做了很多事：查这个商品还有没有库存、你是不是已经抢过了、价格对不对——然后扣掉一个库存、创建一个订单、返回"恭喜抢到了"或"已售罄"。

在这个过程中：
- **你看到的商品图片和按钮** = 前端
- **手机发给服务器的那条"我要买"的消息** = API 请求
- **服务器扣库存、创建订单、返回结果** = 后端

后端不展示界面，它只负责三件事：**接收请求、处理数据、返回结果**。所有你在 App 上看到的信息，都是后端算好了传给前端的。

**为什么要前后端分离？**

同一个后端，淘宝网站能用、淘宝 App 能用、支付宝小程序也能用——它们只是换了不同的"外壳"，里面的下单逻辑一模一样。这就是**关注点分离**：前端只管怎么好看，后端只管业务逻辑正确。

### 1.2 为什么用 Go 语言做秒杀？

秒杀场景的核心挑战就是一个字：**堵**。零点一到，几万人同时点按钮，服务器瞬间被打爆。

Go 的几个特性天然适合这个场景：

| 特性 | 对秒杀的意义 |
|------|------------|
| **goroutine 轻量并发** | 同时处理几万个抢购请求，每个请求在独立的 goroutine 里跑，互不阻塞 |
| **编译成二进制，部署简单** | 秒杀前临时扩容，丢个文件到新服务器上就能跑 |
| **内存占用低** | 同样处理 10000 并发，Go 占的内存是 Java 的几分之一 |
| **标准库 net/http 高性能** | 不需要引入重量级框架就能扛住高 QPS |

双 11 的很多基础设施——Redis、Docker、Kubernetes——就是用 Go 写的。Go 在"高并发后端"这个领域的地位，是由这些实战检验过的。

### 1.3 需求故事：电商秒杀平台

你要做的不是一个"商品展示网站"，而是一个**扛得住秒杀流量冲击的交易系统**。核心用户只有两类人，业务流程极其简单：

**两种角色**

| 角色 | 身份 | 核心诉求 |
|------|------|---------|
| **买家（Buyer）** | 任何想抢便宜货的普通用户 | 看到秒杀商品、到点抢购、付款、收到兑换码/激活码、用完后给评价 |
| **卖家（Seller）** | 电商店主 | 上架秒杀商品（虚拟商品，如优惠券、游戏点卡、会员激活码）、设置库存和价格、确认订单并发放、回复买家评价 |

**业务流程——每个人都见过**

1. 卖家设置一个秒杀商品：原价 99 元的视频会员年卡，秒杀价 9.9，限量 100 个，今晚 8 点整开始
2. 系统开始倒计时，买家看到"距秒杀开始还有 02:35:18"
3. 8 点整，几百个买家同时点击"立即抢购"
4. 前 100 个请求成功扣到库存，创建订单——买家看到"已抢到，请付款"
5. 第 101 个请求发现库存为 0——买家看到"已售罄"
6. 买家付款，卖家后台看到新订单
7. 卖家标记订单完成，买家在订单详情里看到激活码/兑换码
8. 买家给商品打分写评价

**秒杀商品的生命周期**

```
卖家创建（草稿）
    ↓ 设置开始时间
  未开始 ──到点自动──> 进行中 ──库存归零或到结束时间──> 已结束
```

就这么简单，三个状态。秒杀的核心不是复杂的状态机，而是"如何保证第 100 个和第 101 个请求之间库存不会扣错"。

### 1.4 技术栈全景图

| 层级 | 选型 | 在秒杀系统中的作用 |
|------|------|------------------|
| **语言** | Go 1.23 | 高并发处理抢购请求 |
| **HTTP** | `net/http` 标准库 | 路由分发，不引入框架依赖 |
| **数据库** | PostgreSQL | 存用户、商品、订单等结构化数据 |
| **缓存** | Redis | **秒杀的核心**——库存预热到 Redis，下单时直接从 Redis 扣，比查数据库快 100 倍 |
| **消息队列** | Redis Pub/Sub | 订单创建后异步通知卖家 |
| **认证** | JWT 双 Token | 买家/卖家登录 |
| **密码** | bcrypt | 密码哈希存储 |
| **监控** | Prometheus | QPS、下单成功率、库存扣减延迟 |
| **日志** | Logrus + Lumberjack | 记录每一次下单，方便查问题 |
| **部署** | Docker Compose | 一套命令启动所有服务 |

**为什么秒杀必须用 Redis？**

假设一个商品库存 100 件，8 点整 5000 人同时来抢。如果每次扣库存都去更新数据库里的一行，5000 个请求会在 `UPDATE stock = stock - 1 WHERE id = 123 AND stock > 0` 这条 SQL 上排队等行级锁。数据库每秒能处理几百个事务就不错了，后面的请求超时、报错、骂娘。

Redis 单线程处理命令，内存操作，每秒轻松十万次。把库存提前放到 Redis 里，下单时用 Redis 原子操作扣库存，99% 的请求在 Redis 层就被过滤了（要么扣到，要么发现没了），根本不需要打数据库。

### 1.5 环境准备

在动手编码之前，确保你理解这些概念并装好了工具：

- **Go SDK**：安装后跑一下 `go version` 确认可用。理解 `go.mod` 是干嘛的（声明项目依赖）
- **PostgreSQL**：安装并启动，用 `psql` 连进去，亲手建一个 database、建一张表
- **Redis**：安装并启动，用 `redis-cli` 连进去，跑一下 `SET a 1` 和 `GET a` 感受什么叫"内存存储"
- **Docker**：用 `docker-compose up` 一键启动 PostgreSQL + Redis + 你的应用，不需要手动配环境
- **Git**：代码版本管理，理解 `.gitignore` 的作用

## 第二章：兵马未动 — 项目结构设计思维

### 2.1 核心概念：分层架构

**生活化比喻 — 快递分拣中心**

一个快递分拣中心从收货到发出的流程是分层的：

- **收货区**：快递员把包裹卸下来，初步分类
- **分拣线**：机器扫码，按目的地分到不同的出口
- **装车区**：工人把同一目的地的包裹装车发走

如果收货区、分拣线、装车区混在一起，地上堆满包裹，谁也找不到谁的——这就是不分层的后果。

软件的分层也是一个道理：

```
┌─────────────────────────────────────────┐
│          handlers/   (HTTP 处理层)       │  ← 接收请求、检查参数、调用逻辑、返回 JSON
├─────────────────────────────────────────┤
│          database/   (数据操作层)        │  ← 查数据库、读写 Redis、事务管理
├─────────────────────────────────────────┤
│          models/     (数据定义层)        │  ← 买家结构体长什么样、订单有哪些字段
└─────────────────────────────────────────┘
```

**横切关注点**（渗透所有层的公共能力）：

```
┌───────────────┬────────────────┬──────────────┐
│  response/    │  monitoring/   │  logging/    │
│  统一返回格式  │  Prometheus    │  日志记录     │
└───────────────┴────────────────┴──────────────┘
```

**秒杀系统尤其需要清晰分层**

秒杀的下单链路是：Handler 收到请求 → 检查参数 → 调 Redis 扣库存 → 创建订单入库 → 通知卖家。如果 Redis 操作和数据库操作混在 Handler 里，某天你想把"扣库存"从 Redis 换成别的方式，需要把 Handler 里所有相关代码翻出来改。分层之后，Handler 只调 `database.SeckillDeduct(商品ID, 用户ID)`，里面是 Redis 还是数据库，Handler 不关心。

### 2.3 HTTP 路由与 RESTful API 设计

RESTful 的核心思想就一句话：**URL 表示"什么东西"，HTTP 方法表示"干什么"**。

| HTTP 方法 | 干什么 | 秒杀系统中的例子 |
|-----------|--------|----------------|
| `GET` | 查看 | `GET /api/buyer/seckill` → 看秒杀商品列表 |
| `POST` | 创建 | `POST /api/buyer/order` → 下一个秒杀订单 |
| `PUT` | 更新（全量） | `PUT /api/seller/product/{id}` → 修改秒杀商品 |
| `DELETE` | 删除 | `DELETE /api/buyer/order/{id}` → 取消未付款订单 |

**URL 设计实例**

```
✅ 一看就懂的：
GET    /api/buyer/seckill              # 买家看秒杀商品列表
POST   /api/buyer/order                # 买家下单
GET    /api/buyer/order/status?id=123  # 查订单状态
POST   /api/seller/product             # 卖家上架秒杀商品
PUT    /api/seller/product/stock       # 卖家调整库存

❌ 莫名其妙的：
GET    /api/getSeckillList
POST   /api/buyAction
```

Go 标准库 `net/http` 的路由是前缀匹配，不支持路径参数 `{id}`。我们的处理方式：把 ID 放在 Query String 里（`?id=123`），或者手动解析 URL 路径。项目做大之后可以换 gorilla/mux 这种支持路径参数的路由器。

## 第三章：根基 — 数据模型与数据库设计

### 3.1 核心概念：关系型数据库思维

**生活化比喻 — 淘宝订单详情页**

打开淘宝的"我的订单"页面，一条订单看起来很简单，背后却关联了多张表：

- **"iPhone 15 Pro"** → 来自商品表（products）
- **"¥7999"** → 来自商品表或订单表（订单创建时快照了价格）
- **"收货人：张三，北京朝阳区"** → 来自用户地址表
- **"卖家：Apple 官方旗舰店"** → 来自卖家表
- **"物流：顺丰快递 SF123456"** → 来自物流表

淘宝不会把所有这些信息全部塞进一张"订单大表"里——那样的话，如果店铺改名了，每条历史订单里的店铺名都得跟着更新。正确的做法是用 ID 关联：订单表里只存 `seller_id = 42`，店铺名在卖家表里，改一次全部生效。

这就是关系型数据库的核心：**用 ID 做关联，而不是复制数据**。

**关键概念**

| 概念 | 解释 | 秒杀系统例子 |
|------|------|------------|
| **表（Table）** | 一类东西的数据集合 | 买家表、商品表、订单表 |
| **行（Row）** | 一个具体的东西 | 用户张三、商品"蓝牙耳机" |
| **列（Column）** | 东西的属性 | 买家的手机号、商品的价格 |
| **主键（PK）** | 唯一标识一行 | `buyer_id = 42` |
| **外键（FK）** | 指向另一张表的 ID | 订单表 `buyer_id` → 买家表 `buyer_id` |
| **索引（Index）** | 加速查找的辅助结构 | 给 `buyer_id` 建索引，快速查到某人的所有订单 |

关系的三种类型：

```
1:1  — 一个订单对应一次付款记录
1:N  — 一个卖家有多个秒杀商品
N:M  — 一个买家买了多种商品，一种商品被多个买家买
```

### 3.3 PostgreSQL 在秒杀系统中的特殊用途

**1. 事务——下单操作的原子性**

一次下单需要同时做多件事：
1. 在订单表插入一条记录
2. 更新秒杀商品表的 `stock - 1`

事务保证这两步要么全成功，要么全失败——不会出现"订单创建了但库存没扣"或者"库存扣了但订单没创建"。

**2. 行级锁——防止超卖的数据库层兜底**

Redis 扣库存是秒杀的第一道防线（快但不安全），行级锁是第二道防线（慢但绝对安全）：

```
场景：Redis 里的库存是 1，两个请求同时从 Redis 读到 1，都认为自己抢到了
结果：两个请求都去创建订单 → 第二个请求执行 UPDATE stock = stock - 1 WHERE product_id = 123 AND stock > 0 → stock 变成 0，第二个请求没抢到 → 退款
```

这就是"Redis 做高性能过滤 + 数据库行级锁兜底"的双重保障策略。99% 的情况下 Redis 就搞定了，只有边界情况需要数据库出面。

**3. PostGIS 地理扩展——搜索附近店铺**

买家搜"我附近的店铺"不是按距离排序，而是用 PostGIS 的空间索引查"方圆 5 公里内的所有店铺"。自己写经纬度距离计算不仅复杂而且在数据量大时极慢——PostGIS 用专门的 R-tree 索引搞定这件事。

## 第四章：连上线 — 数据库连接与操作

### 4.1 核心概念：数据库连接池

**生活化比喻 — 奶茶店的制作台**

一家奶茶店高峰期可能有 30 个人同时点单，但店里的制作台只有 5 个。点单是一瞬间的事（HTTP 请求进来），但做一杯奶茶要 2 分钟（数据库查询）。30 个订单不可能同时做——只有排到制作台的 5 杯在同时制作，剩下的排队等。

- 制作台数量 = `MaxOpenConns`（最大连接数）
- 正在做奶茶的台子 = 正在使用的连接
- 空闲的台子 = `MaxIdleConns`（空闲连接）
- 一杯奶茶最多占用制作台的时间 = `ConnMaxLifetime`

秒杀场景下，连接池的配置非常关键。因为秒杀开始的一瞬间，几百个下单请求同时到达，每个都要查 Redis + 写数据库——如果 MaxOpenConns 设得太小，请求在数据库层面排队，响应变慢，超时的请求增加，用户体验一塌糊涂。

**连接池的三个核心参数**

| 参数 | 含义 | 秒杀场景建议 |
|------|------|------------|
| `MaxOpenConns` | 最多同时打开几个连接 | 100（根据数据库规格调整） |
| `MaxIdleConns` | 最少保持几个空闲连接 | 10（有备无患） |
| `ConnMaxLifetime` | 单个连接最长活多久 | 1 小时（防止数据库端连接过期） |

我们内置了连接池监控——每 5 分钟输出一次统计，使用率超过 80% 时输出告警日志。

> **设计思考**：秒杀开始时 5000 个请求同时到达，MaxOpenConns 只有 100。这 5000 个请求会怎样？排队排多久？超时了怎么办？

### 4.2 Redis 缓存——秒杀的生命线

**秒杀系统中 Redis 的四种用法**

| 用途 | 具体场景 | 为什么不用数据库 |
|------|---------|----------------|
| **库存预热** | 秒杀开始前，把商品库存同步到 Redis | 数据库扣库存有行锁，极限 QPS 只有几千；Redis 单线程内存操作，轻松十万 QPS |
| **热数据缓存** | 秒杀商品列表、商品详情 | 数据库查一次几毫秒到十几毫秒；Redis 几十微秒 |
| **消息通知** | 买家下单后通知卖家"你有新订单" | 数据库没有推送能力；Redis Pub/Sub 毫秒级推送 |
| **限流** | 限制同一买家每秒的下单次数 | 数据库做不了实时计数，并发写同一行性能爆炸 |

**库存预热——秒杀最关键的准备工作**

```
秒杀 8:00 开始

7:58  — 系统把商品库存 = 200 同步到 Redis key: "seckill:stock:123" → value: 200
7:59  — Redis 里库存准备好了
8:00  — 买家涌入，每次下单先执行 Redis DECR "seckill:stock:123"
         如果返回值 > 0 → 抢到了，继续创建订单
         如果返回值 < 0 → 抢完了，返回"已售罄"
8:00:02 — 200 个库存被抢完（Redis 里只花了 2 秒）
```

**缓存穿透——秒杀中的典型攻击**

攻击者用不存在的商品 ID（比如 ID=-1）反复请求下单接口。缓存里没有这个 ID 的数据，每次请求都穿透到数据库——如果并发量够大，数据库直接被这种"无用请求"打挂。

防御方法：缓存空值——即使商品不存在，也在 Redis 里记一条 `"product:null:-1"`，TTL 设短点（比如 30 秒），下次有人用这个不存在的 ID 来请求，直接从缓存返回"不存在"，不查数据库。

**缓存雪崩——秒杀结束时的隐形杀手**

秒杀 8:00 开始，8:05 结束。8:05 时，所有秒杀商品的缓存（TTL 都设成了 8:10 过期）同时失效。如果这时候有人刷商品列表，几百个请求同时打到数据库——这就是雪崩。

防御方法很简单：给每个缓存的过期时间加一个随机尾巴。比如商品 A 的缓存 TTL = 10 分钟 + 随机 0-3 分钟，商品 B 的 TTL = 10 分钟 + 另一个随机数。这样缓存不会在同一秒集体过期。

> **设计思考**：Redis 的数据全在内存里，如果 Redis 进程突然挂了，库存数据怎么办？你怎么恢复？恢复到什么程度？

`database/` 包里的每个文件只负责一种数据操作：

| 文件 | 操作的数据 | 核心操作 |
|------|----------|---------|
| `postgres.go` | — | 连接池初始化、断线重连（最多 3 次） |

## 第五章：你是谁？— 用户认证与授权

### 5.1 核心概念：认证 vs 授权

**生活化比喻 — 坐高铁**

坐高铁的完整流程：

1. **认证**：你拿着身份证，过闸机刷脸——系统确认"你就是张三"
2. **授权**：系统查你的购票记录——"张三买的是 2 车 5A 号，没有买商务座"——所以你能进 2 号车厢，但不能进商务座

在秒杀系统里：
- **认证** = 登录（输入手机号 + 密码 → 返回一个 Token）
- **授权** = 每次请求时检查 Token → 你是买家，只能看商品列表；你是卖家，可以看到后台订单管理

买家和卖家虽然都是"用户"，但他们看到的界面、能做的操作完全不同。这就是授权的作用——同一个系统，不同的人有不同的权限。

### 5.2 JWT 双 Token 机制

**什么是 JWT？**

JWT 就是一个"加密的身份牌"。你登录成功后，服务器给你一个字符串，之后每次请求都带着它，服务器一看就知道你是谁。

JWT 由三部分组成，用点号分隔：

```
Header.Payload.Signature
```

- **Header**：说清楚用什么算法签名
- **Payload**：存你的用户 ID、角色（buyer/seller）、Token 过期时间等
- **Signature**：用密钥算出来的签名——你改 Payload 里的任何一个字，签名就对不上了，服务器就知道有人篡改了

**双 Token 的设计**

| Token | 有效期 | 用途 |
|-------|--------|------|
| Access Token | 15 分钟 | 实际访问 API 时带着的令牌 |
| Refresh Token | 7 天 | Access Token 过期后，用这个换一个新的 |

为什么要两个？

Access Token 你每次请求都要带着它，它频繁出现在网络传输中，泄露风险高——所以有效期设短一点，15 分钟。丢了也就 15 分钟的事。

Refresh Token 只在需要刷新时才用一次，大部分时间躺在客户端里不动——所以有效期可以长，7 天不用重新登录。

**刷新流程**

```
Access Token 快过期
  → 客户端发 POST /api/auth/refresh，带上 Refresh Token
    → 服务器确认 Refresh Token 没被吊销
      → 发新的 Access Token（15min）+ 新的 Refresh Token（7d）
        → 旧的 Refresh Token 加入黑名单
          → 返回新的一对
```

关键是"旧的 Refresh Token 入黑名单"这一步——如果有个黑客偷了你的 Refresh Token 提前刷新了，你的旧 Token 就失效了，你刷新时会发现 Token 已被用，知道出事了。

### 5.3 密码安全：bcrypt

密码不能明文存数据库——如果数据库被拖库，所有用户的密码直接暴露。存哈希也不行——MD5 和 SHA-256 算得太快了，攻击者用 GPU 一小时能试几十亿个密码。

bcrypt 是故意设计成"慢"的——每次哈希要几百毫秒。用户登录时 200ms 完全感知不到，但对攻击者来说，暴力破解的成本高了几个数量级。

注册流程：明文密码 → bcrypt 哈希 → 存入数据库 `password_hash` 列。登录时用 `bcrypt.CompareHashAndPassword()` 验证——输入密码的哈希和库里的哈希一比对，一致就通过。

> **设计思考**：bcrypt 的哈希每次结果都不一样（因为带了随机 salt），怎么比对？既然结果不一样，数据库里存的到底是什么？

## 安全加固更新（2026-08）

秒杀系统上线后经历了一轮安全审查，发现了 5 个需要加固的点。每个问题都是"少了一行判断"导致的——安全不是做多复杂的事，是把该做的事每一步都做对。

### 1. 下单时间窗口：从状态判断到精确时间比较

**原来的逻辑**：判断秒杀能否下单，只看 `product.Status == "active"`。

**隐藏的问题**：商品状态 `active` 是靠"有人查询商品列表时顺手 UPDATE"来更新的（懒更新）。如果秒杀结束了但没人刷列表，状态还是 `active`，下单接口对直接调用 API 的请求毫无阻挡。

**加固方式**：在状态判断基础上，增加 `time.Now()` 与 `product.SeckillStart` / `product.SeckillEnd` 的精确比较。不管状态字段对不对，服务器时间不会骗人。

```go
now := time.Now()
if product.Status != "active" || now.Before(product.SeckillStart) || now.After(product.SeckillEnd) {
    // 拒绝
}
```

> **设计思考**：为什么不在 `GetSeckillProducts` 里直接更新状态，而是靠列表查询时"顺手"更新？定时任务和懒更新各有什么优劣？

### 2. JWT Token 无过期时间

**原来的逻辑**：JWT claims 只存了 `user_id` 和 `role`，没有 `exp` 标准字段。

**隐藏的问题**：Token 一旦签发就永不过期。截获 Token 的人可以永远冒充这个用户。

**加固方式**：签发时加入 `exp`，设为 24 小时后失效。JWT 库在 `ParseToken` 时自动校验过期时间。

```go
claims := jwt.MapClaims{
    "user_id": userID,
    "role":    role,
    "exp":     time.Now().Add(24 * time.Hour).Unix(),
}
```

> **设计思考**：过期时间设多长合适？15 分钟？24 小时？7 天？各有什么取舍？

### 3. 卖家操作订单缺乏归属校验

**原来的逻辑**：卖家 `SellerAcceptOrder`、`SellerCompleteOrder`、`SellerUpdateStock` 在 JWT 认证通过后，凭 `order_id` / `product_id` 直接操作，不检查"这个订单/商品是不是自己的"。

**隐藏的问题**：卖家 A 可以接卖家 B 的订单、完成卖家 B 的交易、修改卖家 B 的商品库存。同理，买家可以通过 `order_id` 查看他人的订单详情。

**加固方式**：四个接口各加一行归属校验，不匹配返回 403。

| 接口 | 校验 |
|------|------|
| 接单 / 完成 | `order.SellerID != sellerID` → 403 |
| 修改库存 | `product.SellerID != sellerID` → 403 |
| 买家查订单 | `order.BuyerID != buyerID` → 403 |

> **设计思考**：JWT 里的 `user_id` 是从 Token 解出来的，不是客户端传的——为什么这一点对安全性至关重要？如果 `user_id` 是客户端传的会怎样？

### 4. 防重下单增加数据库层兜底

**原来的逻辑**：防重复下单完全依赖 Redis `SETNX`，设置 10 秒过期标记。

**隐藏的问题**：Redis 不保证数据持久化。如果 Redis 重启，标记丢失，同一买家可重复下单。

**加固方式**：在 `ProcessSeckillOrder` 事务内开头增加 `SELECT COUNT(*) FROM seckill_orders WHERE buyer_id=? AND product_id=?`。如果已有订单，事务回滚。Redis 仍然是第一道防线（快），数据库是第二道兜底（稳）。

```
Redis SETNX ──→ 拦截大部分重复
      │ 放行
      ▼
MySQL 事务 ──→ SELECT COUNT ──→ 已有？→ 回滚
                      │ 没有
                      ▼
              INSERT 订单 → COMMIT
```

> **设计思考**：为什么在事务里 SELECT 而不是用 UNIQUE 索引？UNIQUE 索引和 SELECT COUNT 在并发场景下的行为有什么区别？

### 5. Redis 扣库存增加 key 存在性检查

**原来的逻辑**：`DeductStock` 直接对 `seckill:stock:商品ID` 执行 `DECR`。

**隐藏的问题**：Redis 的 `DECR` 对不存在的 key 会从 0 开始减，返回 -1。如果 Redis 预热失败（网络超时、进程崩溃），商品有库存但所有人都买不了。

**加固方式**：`DECR` 前先 `EXISTS` 检查。如果 key 不存在，用 MySQL 查出来的库存值自动预热，然后再 `DECR`。

```go
exists, _ := RDB.Exists(Ctx, key).Result()
if exists == 0 && fallbackStock > 0 {
    RDB.Set(Ctx, key, fallbackStock, 0)
}
return RDB.Decr(Ctx, key).Result()
```

> **设计思考**：这个方案在 Extreme 并发下有两步操作（EXISTS + SET），非原子。极端情况下会不会有问题？如果不接受，用什么方案替代？

### 6. 离线消息：从逐条轰炸到摘要通知

**原来的逻辑**：用户上线后，遍历所有会话，每个会话拉 50 条历史消息，逐条通过 WebSocket 推送给客户端。

**隐藏的问题**：如果用户有 50 个未读会话，上线瞬间收到 50 × 50 = 2500 条 WebSocket 消息。客户端处理不过来，页面卡死。而且推送完立刻调用 `MarkMessagesRead`——用户只是打开 APP，根本没点进任何对话，消息就全被标已读了。

**加固方式**：不再逐条推送，改为只发一条摘要 `unread_summary`。

```
改前：会话A → 拉 50 条 → 逐条 push → 标已读
      会话B → 拉 50 条 → 逐条 push → 标已读
      会话C → 拉 50 条 → 逐条 push → 标已读
      ...
      50 个会话 → 2500 条消息轰炸

改后：遍历会话 → GetUnreadCount(只查数量)
      → 汇总成 UnreadSummary{total: 30, conversations: [...]}
      → 发一条 push → 结束
      用户点进具体会话时通过 HTTP GetMessages 拉详情并标已读
```

新增了两个数据结构：

| 结构 | 作用 |
|------|------|
| `UnreadSummary` | 总未读数 + 每个会话的摘要列表 |
| `UnreadConversation` | 单个会话的摘要：对方是谁、几条未读、最后一句说了啥 |

**为什么不在上线时标已读**：用户只是收到了"有 30 条未读"的通知，并没有真正点开看。真正标已读的时机应该放在 `HandleGetMessages`——用户打开聊天页面那一刻。

> **设计思考**：如果用户有一万个未读会话，上线时还是一万个 GetUnreadCount 查询——怎么做优化？用一条 SQL 聚合查询能解决吗？

---

### 反思：安全不是大工程，是一堆小判断

五个安全改动加上一个架构优化，加起来不到 80 行代码。每一处都是"少了一句 `if`"或"差了最后一步"——但对系统的影响从不一致数据、越权操作、消息轰炸、到完全不可用。

核心思路只有一条：**永远不要假设上一步一定成功。** 状态可能没更新、Token 可能被截获、归属可能不对、Redis 可能挂了、用户可能没看消息——在每一步做完之前，先确认上一步真的做完了。
